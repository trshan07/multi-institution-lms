# Multi-Institution SaaS LMS — Technical Architecture Specification

Version 1.0 · Moodle-inspired · Multi-tenant SaaS · Enterprise architecture

Your LMS will be a multi-institution Software-as-a-Service (SaaS) platform, where schools, universities, training institutes, and online academies can operate their own learning environments within one shared platform.

The most important architectural decision is that each institution must experience the LMS as its own independent system, even when the underlying application infrastructure is shared.

For example:

Your LMS SaaS Platform

Shared infrastructure · Central platform administration

University A

university-a.lms.com

School B

school-b.lms.com

Academy C

academy-c.lms.com

Each institution has its own users, courses, enrollments, files, branding, permissions, and academic configuration.

My recommendation is a control-plane/data-plane architecture, using a modular monolith for the core LMS and independently scalable workers for media processing, background tasks, and integrations.

## 1. Key architecture decisions

| Decision              | Recommended design                                 |
| --------------------- | -------------------------------------------------- |
| SaaS tenancy          | Shared application, logically isolated tenant data |
| Tenant identification | Verified custom domain or institution subdomain    |
| Database              | PostgreSQL with `tenant_id` and row-level security |
| Core backend          | NestJS modular monolith                            |
| Frontend              | Next.js portals with tenant-aware branding         |
| Authentication        | OIDC identity provider, tenant-aware memberships   |
| Authorization         | Contextual RBAC + attribute-based policies         |
| Media storage         | Private S3-compatible object storage               |
| Background jobs       | BullMQ / Redis, transactional outbox               |
| Extension system      | Versioned learning-activity interfaces             |
| Scaling               | Horizontal API replicas, workers, managed services |
| Enterprise isolation  | Optional dedicated database or deployment tier     |

A shared database is appropriate initially, but tenant isolation must be enforced in multiple layers—not just by adding a `WHERE tenant_id = ...` condition in application code.

The control plane manages subscriptions, institutional domains, tenant provisioning, and platform operations. The data plane manages actual teaching and learning.

This separation also makes it easier to move a large institution onto dedicated infrastructure later.

## 3. Tenant isolation strategy

I recommend three supported deployment tiers.

| Tier       | Isolation model                                    | Best for                                             |
| ---------- | -------------------------------------------------- | ---------------------------------------------------- |
| Standard   | Shared database, shared schema, tenant-scoped rows | Small and medium institutions                        |
| Enterprise | Dedicated tenant database, shared application      | Larger institutions                                  |
| Dedicated  | Dedicated database and application deployment      | Institutions with contractual isolation requirements |

Start with Standard, but introduce a `TenantConnectionResolver` abstraction so the application can route data access to a dedicated database later without rewriting every module.

Important rules:

- Tenant context is resolved from a verified domain mapping, not blindly trusted from a request header.
- User authentication establishes identity, but membership establishes which institution the user can access.
- All tenant-owned records contain a tenant identifier.
- Background jobs carry a validated tenant context.
- Object-storage keys are tenant-scoped, with access controlled by backend authorization.
- Cache keys, rate limits, search indexes, and analytics are tenant-aware.
- Super administrators cannot silently bypass audit controls.

A user can belong to multiple institutions with different roles. For example, someone might be a lecturer at one institution and a student at another.

## 4. Detailed database design and ERD

Use two PostgreSQL logical schemas or databases:

- `platform`: tenant registry, subscription plans, domain mappings, provisioning status, billing metadata.
- `lms`: institution-owned academic and learning data.

For the first release, these may be schemas in one managed PostgreSQL cluster. For enterprise tenants, route the `lms` workload to a dedicated database.

### Required database constraints

Use UUID primary keys and tenant-scoped composite foreign keys for all tenant-owned relationships.

Examples:

```
UNIQUE (tenant_id, course_code)
UNIQUE (tenant_id, course_id, offering_code)
UNIQUE (tenant_id, offering_id, user_id)
UNIQUE (tenant_id, question_id, version)
UNIQUE (tenant_id, user_id, activity_id)
```

For composite foreign keys, referenced tables must have matching unique constraints, such as `UNIQUE (tenant_id, id)`.

Indexes should be selected from real query patterns. Common starting indexes include `(tenant_id, status)`, `(tenant_id, offering_id, user_id)`, and `(tenant_id, created_at DESC)`.

### PostgreSQL row-level security

Example policy:

```
ALTER TABLE lms.courses
ENABLE ROW LEVEL SECURITY;

ALTER TABLE lms.courses
FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation
ON lms.courses
FOR ALL
TO lms_runtime
USING (
  tenant_id =
  NULLIF(
    current_setting('app.tenant_id', true),
    ''
  )::uuid
)
WITH CHECK (
  tenant_id =
  NULLIF(
    current_setting('app.tenant_id', true),
    ''
  )::uuid
);
```

Set the tenant context only after authentication and membership verification, within the same transaction as the queries:

```
BEGIN;

SELECT set_config(
  'app.tenant_id',
  $1,
  true
);

-- Authorized application queries

COMMIT;
```

The runtime database role must not own these tables, be a superuser, or have `BYPASSRLS`. Use separate migration and runtime roles. A connection pool must not accidentally reuse tenant context between requests.

RLS is a defense-in-depth boundary; it does not replace application authorization, especially for grades, private files, and cross-course permissions. PostgreSQL documents both the policy semantics and the special privileges that can bypass them.&#x20;

## 5. Backend module boundaries

Each module should own its data access, domain rules, public interfaces, and events.

| Module        | Owns                                       | Public interfaces / events               |
| ------------- | ------------------------------------------ | ---------------------------------------- |
| Tenant        | Tenant settings, provisioning, domains     | `TenantCreated`, `TenantSuspended`       |
| Identity      | Users, memberships, SSO mappings           | `UserJoinedTenant`                       |
| Authorization | Roles, capabilities, contexts              | `authorize()`                            |
| Academic      | Departments, programs, terms, cohorts      | `TermCreated`                            |
| Course        | Catalog, offerings, sections               | `CoursePublished`                        |
| Enrollment    | Methods, eligibility, enrollment lifecycle | `StudentEnrolled`, `EnrollmentSuspended` |
| Content       | Activities, resources, availability        | `ActivityPublished`                      |
| Media         | File metadata, upload sessions, scanning   | `AssetReady`                             |
| Assessment    | Question bank, quizzes, attempts           | `QuizAttemptSubmitted`                   |
| Assignment    | Submission lifecycle, rubrics              | `AssignmentSubmitted`                    |
| Gradebook     | Grade items, weights, grade history        | `GradePublished`                         |
| Progress      | Completion and mastery rules               | `CourseCompleted`                        |
| Communication | Forums, announcements, notifications       | `NotificationRequested`                  |
| Analytics     | Reporting projections, event aggregation   | `LearningEventRecorded`                  |
| Integration   | LTI, SCORM, SIS, webhooks                  | `ExternalSyncCompleted`                  |
| Billing       | Plans, quotas, subscriptions               | `SubscriptionChanged`                    |

### Rules for module communication

A command such as `EnrollStudent` should be handled synchronously by the Enrollment module. Once committed, it writes an outbox event that can asynchronously trigger a welcome notification, analytics update, and progress initialization.

The Course module should not directly modify the Enrollment module's tables. Likewise, the Quiz module should not directly overwrite gradebook records.

For critical operations, use a domain service interface:

```
interface EnrollmentService {
  enroll(command: EnrollStudentCommand):
    Promise<EnrollmentResult>;

  suspend(command: SuspendEnrollmentCommand):
    Promise<void>;

  isActive(
    tenantId: string,
    offeringId: string,
    userId: string
  ): Promise<boolean>;
}
```

All writes that change authoritative academic state should have a single owning module. This prevents duplicated logic and conflicting records.

## 6. API design

Use a versioned REST API with OpenAPI specifications, OAuth/OIDC authentication, and consistent error handling.

Base endpoint:

`https://api.yourlms.com/v1`

Tenant selection should come from the verified hostname and authenticated membership. For a central API domain, use a validated tenant-selection mechanism bound to the session or token, rather than accepting arbitrary tenant IDs.

### Core API endpoints

| Method | Endpoint                              | Purpose                       |
| ------ | ------------------------------------- | ----------------------------- |
| POST   | `/platform/tenants`                   | Provision an institution      |
| GET    | `/me/tenants`                         | List user's institutions      |
| GET    | `/tenant/settings`                    | Get institution configuration |
| PATCH  | `/tenant/settings`                    | Update branding and settings  |
| GET    | `/users`                              | List institution users        |
| POST   | `/users/invitations`                  | Invite staff or students      |
| GET    | `/courses`                            | Search course catalog         |
| POST   | `/courses`                            | Create a course               |
| POST   | `/courses/{id}/offerings`             | Create an offering            |
| POST   | `/offerings/{id}/enrollments`         | Enroll a student              |
| GET    | `/offerings/{id}/participants`        | List enrolled users           |
| POST   | `/sections/{id}/activities`           | Add a learning activity       |
| POST   | `/media/upload-sessions`              | Start secure upload           |
| POST   | `/assignments/{id}/submissions`       | Submit assignment             |
| POST   | `/quizzes/{id}/attempts`              | Start quiz attempt            |
| PUT    | `/attempts/{id}/answers/{questionId}` | Save answer                   |
| POST   | `/attempts/{id}/submit`               | Finalize quiz                 |
| GET    | `/offerings/{id}/gradebook`           | Retrieve authorized gradebook |
| GET    | `/me/progress`                        | Retrieve student progress     |
| GET    | `/reports/course-completion`          | Completion report             |

Every collection endpoint should support bounded pagination and authorized filters. Mutation endpoints should support idempotency keys where duplicate requests could create duplicate records.

### Example enrollment request

```
POST /v1/offerings/9b12.../enrollments
Authorization: Bearer <access_token>
Idempotency-Key: 49e7...
Content-Type: application/json
```

```
{
  "userId": "5c8f...",
  "method": "MANUAL",
  "startsAt": "2027-01-15T00:00:00Z"
```

A successful response:

```
{
  "id": "enr_01J...",
  "status": "ACTIVE",
  "offeringId": "9b12...",
  "userId": "5c8f...",
  "enrolledAt": "2027-01-10T09:30:00Z"

```

The server derives the tenant from the authenticated request context, checks the operator's enrollment permission, validates the student's tenant membership and offering eligibility, and commits the enrollment transaction.

### Standard error contract

```
{
  "type": "https://api.yourlms.com/problems/forbidden",
  "title": "Forbidden",
  "status": 403,
  "detail": "You cannot manage enrollment for this course.",
  "requestId": "req_01J..."
}
```

Use HTTP Problem Details (RFC 9457), with no sensitive internal information exposed in error messages.

### Authorization context hierarchy

Platform context

SaaS operator only

Institution context

Institution administrator, tenant staff

Department / Program context

Course offering context

Activity context

Quiz, assignment, file, discussion

### Permission matrix

Default role permissions; tenant administrators can configure controlled variations.

| Capability                | Tenant Admin | Teacher     | Student |
| ------------------------- | ------------ | ----------- | ------- |
| Manage tenant users       | ✓            | —           | —       |
| Create courses            | ✓            | Conditional | —       |
| Manage course content     | ✓            | ✓           | —       |
| Enroll students           | ✓            | Conditional | —       |
| Upload learning resources | ✓            | ✓           | —       |
| Create quizzes            | ✓            | ✓           | —       |
| Attempt quizzes           | —            | —           | ✓       |
| Submit assignments        | —            | —           | ✓       |
| Grade students            | ✓            | ✓           | —       |
| View own grades           | Conditional  | Conditional | ✓       |
| View course analytics     | ✓            | ✓           | —       |
| Manage billing            | ✓            | —           | —       |

The matrix is only a default policy. A teacher's capabilities are scoped to assigned courses, and a student's capabilities require valid enrollment and activity availability.

### Authorization evaluation

An action is allowed only when all applicable conditions are satisfied:

\\[ \text{Allow} = \text{TenantValid} \land \text{MembershipActive} \land \text{CapabilityGranted} \land \text{ResourcePolicySatisfied} \\]

For example, submitting an assignment additionally requires active enrollment, submission availability, and a valid deadline or accommodation.

Explicit deny rules should override inherited grants. A role at a higher context may grant a capability to descendants, but never across institution boundaries.

Keep application containers in private subnets, with public ingress through the load balancer. Use VPC endpoints where appropriate and tightly scoped IAM roles for each workload.

For high availability, use at least two Availability Zones, redundant application replicas, database failover, health checks, and tested recovery procedures.

### Event processing reliability

BullMQ is suitable for initial background workloads, but important events should first be written to an outbox table within the business transaction.

A dispatcher then publishes them to the queue. Consumers should be idempotent, retry transient failures, and send permanently failing jobs to a dead-letter workflow.

For workloads requiring stronger queue isolation or durability, use SQS with dedicated consumer workers. Do not treat Redis cache persistence as the authoritative record of academic events.

## 10. Tenant onboarding workflow

1

Institution registration

Capture institution details, administrator identity, requested plan.

2

Subscription activation

Validate billing or trial eligibility and allocate quotas.

3

Tenant provisioning

Create tenant records, defaults, roles, and storage configuration.

4

Domain configuration

Issue default subdomain, verify optional custom domain and TLS.

5

Administrator invitation

Activate first tenant administrator through identity provider.

6

Academic setup

Configure departments, terms, programs, cohorts, and grading policies.

7

Launch

Enable the institution and begin monitoring onboarding health.

Provisioning must be idempotent and resumable. If domain verification fails, for example, the system should not duplicate the tenant or subscription when retried.

Tenant suspension should block ordinary LMS access without deleting academic records. Deletion should be a separately authorized, retention-aware process.
